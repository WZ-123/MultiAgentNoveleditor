### EC-13: 重复导入同一个文件
- **场景**: 用户导入了同一个文件两次
- **影响**: 创建了两个相同的临时项目，用户困惑，浪费磁盘空间和 AI token
- **修复建议**: 
  导入前检查是否已有相同文件正在 staging 中。使用文件路径 + 文件大小 + 前 1024 字节的 SHA256 作为指纹，存储在 staging 注册表的 `sourceFingerprint` 字段。创建新 staging 前先比较指纹。若检测到重复：
  1. 提示用户"此文件已在 X 时间导入过"
  2. 提供选项：跳过（复用已有 staging）/ 重新导入（创建新 staging，旧 staging 标记为废弃）
  3. 若已有 staging 的分析已完成，直接展示分析结果而非重新分析
  另外在 `listStagingProjects()` 返回中增加 `sourceFiles` 字段，供前端展示。
- **实施步骤**:
  1. `stagingProject.js` 的 `createStagingProject` 增加 `sourceFingerprint` 计算和比较
  2. `stagingRegistry.json` 的条目增加 `sourceFingerprint` 和 `sourceFiles` 字段
  3. ImportNovelPanel 在解析完成后调用新的检查 IPC `mana:import:checkDuplicate`
  4. 若检测到重复，在 UI 中弹出确认对话框
  5. `getStagingProject` 返回数据中包含 `sourceFiles`（目前已有 `novelMeta.importMeta.sourceFiles`）
- **是否要修复**: 需要修复
- **已修复**: ✅ 2026-05-06 — `_computeFingerprint()` 使用文件路径+大小+前1024字节 SHA256；`checkDuplicateImport()` 比对活跃 staging；UI 提供「复用已有结果」和「重新导入」选项；复用时会自动检测是否已分析并跳过

### EC-14: 超长文本截断
- **场景**: 小说文本超过 60,000 字符（约 15,000-20,000 字中文），这在长篇小说中非常常见。当前实现直接截断到 60K 字符，后半部分角色和剧情完全丢失。
- **影响**: 
  - 超出 60K 字符的角色、世界观、剧情信息全部丢失
  - 分析结果不完整，用户可能没注意到截断警告
  - 对于 100 章以上的长篇小说完全不可用
- **修复建议** — 分片分析 + 合并结果:

  **Step 1: 智能分片**
  不再硬截断到 60K。在自然边界处切分：
  - 优先在章节标记处切分（`# 第X章`、`Chapter X` 等）
  - 若某章本身超过 60K，在段落边界（`\n\n`）切分
  - 每片不超过 40K 字符（给 AI 回复留出 20K 的 buffer）
  - 记录每片的章节范围，用于合并时的上下文

  **Step 2: 逐片分析**
  每个分片独立运行全套分析（角色/势力/时间线/世界观/大纲/文风）：
  - 分片 N 分析时，提供前一片的分析摘要作为上下文："前面已识别角色: [角色A, 角色B]；前面剧情: [摘要]"
  - 这样每个分片能继承前文的角色和剧情知识

  **Step 3: 合并结果**
  所有分片完成后，按规则合并：
  - **角色**: 同名角色合并字段，取信息最丰富的那个（非空字段优先，长描述优先）
  - **势力**: 同名势力合并，成员列表去重合并
  - **时间线**: 按时间戳合并排序，去重（相似度>0.8 的事件视为同一事件）
  - **世界观**: 合并 lore 文本（追加模式），合并 places 数组（去重同名地点）
  - **大纲**: 按分片顺序拼接，每个分片的概要前标注 `[第N片: 章节X-Y]`
  - **文风**: 取第一片的完整分析 + 后续片的差异部分

  **Step 4: 全局一致性审查**
  合并完成后，用 AI 做一次全局审查：
  - 输入：合并后的角色列表 + 大纲
  - 检查：同一角色是否被识别为不同名字（别名问题）、剧情线是否连贯
  - 输出：修正后的统一版本

- **实施步骤**:
  1. `src/main/import/analyzer.js` 增加 `_splitIntoChunks(text, maxChars=40000)` — 智能分片函数
  2. 修改 `startAnalyses()` — 检测文本长度，超限时自动分片
  3. 新增 `src/main/import/resultMerger.js` — 合并多片分析结果
  4. 修改 `finalizeAnalyses()` — 分片模式下调取合并逻辑
  5. ImportNovelPanel 在 UI 中显示分片进度："正在分析第 N/M 片…"
  6. 新增 `sa-import-reviewer` 子 agent — 全局一致性审查

- **是否要修复**: 需要修复
- **已修复**: ✅ 2026-05-06 — `resultMerger.splitIntoChunks()` 在章节/段落边界切分；`analyzer.js` 逐片分析并传递前情摘要；`resultMerger.mergeChunkResults()` 合并角色/势力/时间线/世界观/大纲/文风；UI 显示分片进度；`sa-import-reviewer` 子 agent 已注册

## 前端数据流完整性

### EC-15: IPC 返回格式不匹配
- **场景**: 后端修改了返回字段名但前端未同步更新
- **影响**: React 渲染崩溃（如 object 当 string 渲染）
- **修复建议**: 所有渲染使用 `s()` 安全转换函数；前后端共享类型定义
- **是否要修复**: 
- **已修复**: ✅ — DataTabContent 和 NovelDataBrowser 已全部使用 s() 转换

### EC-16: WebSearch 超时/失败
- **场景**: 网络不可用、萌娘百科宕机
- **影响**: 角色补全静默跳过
- **修复建议**: 已有错误日志和静默回退，可在 UI 中标注"联网补全失败"
- **是否要修复**: UI标注的同时，添加一个重试按钮，如果是萌百的问题就明确说明这个信源api有问题，如果是无法联网就说联网补全失败，请用户改善网络环境后再试，单个信源无法联网时自动将临近文化圈的信源也纳入搜索途径，用户点击重试就可以调用到。若还是有问题则扩展到全球其他地区的信源。
- **已修复**: ✅ 2026-05-06 — 三级回退：主文化圈源 → 临近文化圈源(如 CN→JP) → 全局 DuckDuckGo。每个角色标记 `_enrichmentStatus: success|search-failed`

### EC-17: mergeEngine 会话泄漏
- **场景**: 用户多次进入合并模式但未退出
- **影响**: 内存中的 _sessions Map 积压
- **修复建议**: 添加 TTL 过期机制或限制最大会话数
- **是否要修复**: 需要修复
- **已修复**: ✅ 2026-05-06 — MAX_SESSIONS=10，超限时淘汰最旧的会话
