# 统一开发与验收工作流

2026-09-22：用户确认采用。适用于本项目开发、修复和验收，也是项目 ux-dev-flow 技能引用的方法文档。本文是工作流的唯一正文；具体架构见 [系统总览](system-overview.md)，执行语义见 [运行契约](codex-native-runtime-contract.md)，命令和发布要求见 [开发与发布](development-and-release.md)。

**各模块分别正确，不等于产品完整正确。每次修改都要检查改动本身、关联系统和受影响的完整用户流程。解耦减少牵连，关联测试发现牵连，两者缺一不可。**

本文规定如何工作，不宣称现有实现已经满足要求；当前偏差见 [缺陷清单](edge-cases.md)。

## 一、完整工作流

### 1. 开始前：确认现状和本次目标

检查当前项目、工作目录、源码、已有改动、上次工作记录和未完成事项，明确用户要做什么、实际结果、正确结果及本次范围。区分此前已有改动与本次修改，避免覆盖或混入其他工作。

启动脚本、版本、端口、路由和测试数据从当前项目确认，不从历史聊天或全局记忆猜测。不把之前的计划当成已经实现的功能。

### 2. 从用户实际入口复现问题

按用户实际路径检查，例如：打开小说 → 输入修改要求 → 读取资料 → 展示修改 → 确认 → 保存 → 页面显示结果。写清入口、请求、目标项目/资源、期望可见结果和需要差异确认的动作。优先使用隔离测试数据，避免影响真实内容。

- 能稳定自动复现的，建立自动检查。
- 暂时不能自动复现的，记录步骤、触发条件和观察证据。
- 仅从代码发现的问题标为“静态发现”，不声称已经实际复现。

测试不能替产品补齐用户本来不需要提供的内部参数。直接调用后端的测试可以保留，但不能代替用户入口测试。

### 3. 修改前：检查根因和关联影响

沿调用、数据和事件关系检查，不只看报错函数：

| 要查什么 | 要回答的问题 |
| --- | --- |
| 上游调用 | 谁触发它？传入的信息是否正确？ |
| 状态归属 | 项目、对话、任务、选区分别属于谁？ |
| 下游依赖 | 哪些模块消费结果或接收事件？ |
| 异常处理 | 失败、拒绝、中断后，各处变成什么状态？ |
| 用户反馈 | 界面结果是否有实际执行证据？ |

据此确定修改与回归范围。多个问题来自同一根因时可以一起修；不机械地按症状加补丁，也不顺带做无关重构。批次过大时按依赖关系拆分，不能仅按审计问题的编号拆分。

### 4. 实现时：减少隐含依赖，明确交接规则

解耦是减少隐含联系，不是单纯增加文件和抽象层：

- 通过明确接口和事件协作，不偷偷依赖其他页面或模块的临时状态。
- 明确数据和状态的更新责任，避免多处维护互相矛盾的结果。
- 同一个事实有唯一权威来源；是否保存成功以实际提交结果为准。
- 明确绑定项目、对话、任务、确认与修改目标。
- 改变接口行为时，同步检查调用方和消费方。
- 优先修复现有链路，不为绕过问题再建一套并行机制。

行为规则改变时，同步更新已有领域说明、契约和相应验收用例，不额外堆积重复文档。

### 5. 验证时：覆盖三个层面

| 层面 | 验证内容 |
| --- | --- |
| 改动本身 | 原问题是否解决，输入输出和边界条件是否正确 |
| 关联系统 | 调用、事件、共享状态和错误处理是否受到影响 |
| 用户流程 | 用户能否从实际入口完成目标，并看见准确结果 |

按影响范围选择检查：不能只测原问题，也不要求每改一行就重跑全部测试。状态管理修改重点检查切项目、切对话、运行中切换、后续“继续”和重复发送；写入修改重点检查确认、拒绝、版本冲突、中断及部分保存。场景按正常 T、异常 E、边界 B、状态转换 S 分类，参考下方矩阵。

- 单元测试检查局部规则；集成测试检查模块交接；用户流程测试检查实际入口到结果。
- 复用现有测试入口，使用隔离小说数据和模拟服务构造稳定场景；真实模型测试只证明模拟服务无法证明的模型行为和兼容性，结果分开记录。
- 运行适合本次改动的项目构建及必要检查；前端构建不能代替安装包或端到端验收。纯文档变更检查内容、引用及入口，不冒称完成产品验证。
- 界面变化需要实际查看，保存成功需要正式资源读回核验；核对请求身份、工具挂载、读取、批准、提交与界面反馈是否对应。
- 截图存在不代表画面合格，界面说成功不代表数据已保存，模拟通过不代表真实模型通过。具体视觉规则见下方证据要求。

### 6. 检查失败后：分清原因，再继续

区分产品代码问题、测试自身问题、环境或外部服务限制。修正对应原因后重新验证，不因测试难跑而降低标准、删除功能或把未验证写成通过。

无法解决的限制必须说明影响哪些结论；不受影响的工作继续完成。

### 7. 每批结束：检查差异，留下可接续记录

检查本批代码差异，确认没有夹带无关修改、覆盖已有工作或遗漏关联变更。在已有任务记录或审计报告中维护下表，不为每次工作另建重复记录体系：

| 问题与根因 | 本批改动 | 验证入口、环境和结果 | 未验证项 | 剩余工作与下一步 |
| --- | --- | --- | --- | --- |
| 填写实际发现 | 填写实际修改 | 命令/步骤、日期、范围及证据链接 | 明确限制 | 区分计划与已完成 |

缺陷登记到现有清单；可重复执行的回归加入现有测试入口，不只在文档里写“下次记得测”。机器相关 URL 和环境信息记在该次验证记录中，不当成通用默认值；不得记录密钥或测试凭据。

### 8. 区分本批完成与整条流程完成

- **本批完成**：本批问题已验证，受影响的关联检查通过。
- **整条流程完成**：相关修复批次结束后，重新走通完整用户流程，包括关键异常路径。

报告分别说明代码检查、模拟验证、真实模型验证和界面验证。不用局部通过代替产品完成，不将历史产物、脚本存在或计划当作当前证据。

## 二、说人话的版本

**不要再把“这个零件没问题”说成“这台机器能用了”。**

1. **先看清现在是什么情况。** 哪些代码已经改过、上次做到哪里、这次解决什么，先弄明白。
2. **照着用户的操作重现问题。** 聊天里遇到的，就从聊天里检查，不能偷偷替系统准备好参数。
3. **找原因，也看看会牵连谁。** 谁把数据交给它、谁等它的结果，都要查。
4. **同一个原因引起的问题一起修。** 不东补西补，也不借机重写无关功能。
5. **让模块之间的关系清楚。** 聊天能力不应随页面切换偷偷变化；谁负责什么、失败怎么办，要有明确规则。
6. **修完检查三件事。** 原问题好了没有？依赖它的功能坏了没有？用户操作一遍能不能完成？
7. **不只试顺利的时候。** 按影响范围检查切换、停止、拒绝、重复点击和保存失败。
8. **把检查和进度留下来。** 下次能重复检查，知道哪里完成、哪里未完成，不靠聊天记忆。
9. **凭实际结果说话。** 说保存就读回确认，说界面好了就打开看，没验证就明确说没验证。

**解耦让一次修改少牵连别处；关联检查确认别处没被弄坏；完整流程验收确认用户最终能用。三件事都要做。**

## 必测转换矩阵

| 流程 | 正常 | 异常/转换 |
| --- | --- | --- |
| 聊天修改 | 用户直接要求修改资料 | 讨论后转修改、切换项目/章节/设置页、旧会话恢复 |
| 选区编辑 | 明确非空选区 | 仅光标、选区变化、整章请求、选区外差异 |
| 批准保存 | 确认差异后正式读回 | 拒绝、撤销授权、冲突、已保存后中断 |
| 并发 | 一轮完成再发送 | 双击发送、多对话、后台任务迟到事件 |
| 导入 | 暂存→审阅→提交 | 解析/分析失败、重复导入、切换目标、取消/恢复 |
| 补全 | 正确二创角色与网页 | 同名、无原作、失败来源、部分成功、用户编辑冲突 |
| 周边服务 | 本地与远端结果分别展示 | 离线、重试、过期会话、重复提交 |

## 证据要求

截图生成不等于验收通过。必须确认无空白、加载遮罩、错误弹层、遮挡、溢出，且目标状态可见。对外提供的截图放入项目 `qa-screenshots/`、`artifacts/` 或可访问输出目录并给出链接。

构建、类型/导入/运行时错误要记录；失败不得以截图存在掩盖。只有构建成功也不能宣称端到端自测通过。AI 文本不作为读写事实，保存必须提供宿主结果及正式资源读回。测试客户端保持静音，除非当次明确要求验证声音。
