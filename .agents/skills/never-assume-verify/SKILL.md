# 铁律：改完必须验证，不假设

## 血的教训

### 教训一：脚本改文件不验证写入
使用脚本（Python/sed 等）修改 JS 文件后，脚本匹配失败（静默无输出），
改动实际上没有写入。但没有检查文件内容、
没有重新构建、没有打开页面查看 DOM，直接声称功能已完成。
用户打开页面发现功能不存在，浪费信任。

### 教训二：逐键追踪写入→读回链路（2026-05-10）
修复 outline 写入截断时犯了两个错误：
1. 只修复了字段级丢失（`{ id, title, summary }` → `{ ...n }`），
   没发现 volume/section 节点**根本没出现在 `nodes.json` 里**——
   `writeHierarchicalOutline()` 的 `allNodes` 数组只 push 了 scene 级节点。
   修复完说「应该好了」，实际上 `read_outline_nodes` 仍然读不到数据。
2. 同一段代码有两层 bug，只修第一层是不够的。
3. 只有在**实际写入一个包含所有字段的测试数据 → 读取 `nodes.json` 检查每个节点**后，
   才发现真正的缺失。之前的「我看了看代码，没问题」毫无价值。

## 铁律

任何修改后，必须做以下**至少一项验证**：

1. **构建验证** — `npx vite build` 或 `node -c` 通过（只证明编译不报错）
2. **文件内容验证** — `grep` 或 `Read` 确认改动行确实写入了文件
3. **运行时验证** — 打开页面/工具，实际点击操作确认功能可用
4. **测试验证** — 运行自动化测试覆盖改动的代码路径

## 用脚本改代码的陷阱

- Python/sed 字符串转义和 JS 文件实际内容可能不匹配
- 静默失败：`str.replace(old, new)` 没找到 `old` 时不报错、原样返回
- 必须检查返回值，或在 replace 后 `print` 确认
- 最佳实践：改完立刻 `grep` 目标字符串确认写入
- 文件路径参数不能忘（如 `Edit` 工具的 `file_path`）

## 检查清单

提交任何改动前：

1. [ ] 文件改动确实写入了（`grep` 或 `Read` 确认）
2. [ ] 构建通过（`vite build` / `node -c`）
3. [ ] 功能可实际使用（不是「应该能用」）
4. [ ] 旧功能没有因改动而损坏
