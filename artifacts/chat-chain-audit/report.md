## 未计入数量的风险

1. 异步加载旧结果覆盖新状态：loadThreads、loadActive、授权/进度加载没有取消或请求版本校验。快速切换时存在乱序回写风险，未做延迟浏览器测试。
2. 工具失败恢复政策：任意 item_completed.status=failed 都触发整回合 interrupt。对错误资源参数、可重试工具失败等是否应允许模型纠正，需要区分错误类型并做真实运行时测试，不能一概认定为故障。
3. 完成语义：现有测试明确允许字数未达目标但 goalVerified=true；review/read 等路径也缺少任务特定证据门槛。这是当前设计选择与“目标已完成”文案之间的风险，不是本次新增回归结论。

### 当前结论与证据边界

11 项源码问题仍成立，但不是 11 个互不相关的根因，归为下面 4 组。重新运行原探针，反例断言均成立；产出 11 条观察记录，不能把观察条数等同于 11 项缺陷都做过独立 UI 复现。

- 当前证据：[复审探针结果](review-probe-results.json)、[时间/环境/源码 hash 基线](review-baseline.json)。工作区已有大量未提交变更，本轮未改动这些业务文件，也不能用 HEAD 代表实际审查版本。
- KB-01、03、07、08、09、11 有生产方法及隔离存储验证；KB-04 有宿主校验与组件发送逻辑验证；KB-05、10 有组件逻辑验证；KB-02、06 为源码路径确认。
- 原组件探针以 hook 替身执行组件函数，useEffect 不运行，部分状态直接预置。它能帮助验证局部逻辑，不能证明 React 生命周期、迟到事件和真实点击的全部后果。上述 UI 结论仍需实际入口验收。
- KB-07 限定为“宿主任务分类和进度缺失”；不能据此说模型一定忘记前文，也不能简单永久继承上一次 Skill/选区。
- KB-08 是聊天结果投射缺失，不是所有日志丢失；ledger 仍记录正式提交。KB-09 的已显示文本可能消失，不意味着已正式保存的小说被撤销。
- KB-11 证明两个普通聊天 start 被宿主接受，不证明原生 App Server 执行了两个回合，更不证明同时提交了两个小说写入事务。

### 根因一：运行归属由面板临时状态代管，发送又缺少完整的启动边界

对应 KB-04、05、10、11。AiChatPanel 把当前显示的对话与当前执行的任务混为一谈；后端虽有运行表，却未在异步准备前完成占位，也未校验历史所属项目。发送前保存、消息落盘和运行启动分散处理，错误和重试缺少统一归属。

| ID | 具体修法（待实施） | 必须检查的关联点 |
| --- | --- | --- |
| KB-04 | 当前项目改变时选择该项目的对话，草稿按项目/对话保存；异步加载带请求版本，拒收旧结果。宿主在绑定原生线程/创建镜像前验证 history.novelId 与请求一致，并校验 userMessageId 属于该对话；不偷偷移动对话 | 切换项目、新建/删除对话、历史分支、LAN 客户端；发起后切页面不改变运行目标 |
| KB-05 | 使用宿主的运行/批准快照作为事实源，UI 按 conversationId/runId 展示。切换只改变视图，后台事件继续归档。增加有版本的快照读取，订阅事件后合并快照，避免丢事件/旧快照覆盖新事件 | preload、IPC、LAN API 同步；确认和停止绑定具体 run，旧确认不可作用新运行；返回对话能恢复等待批准状态 |
| KB-10 | 从发送前保存开始包住整个准备过程；保留原文和已捕获目标。区分“消息未保存”“已保存但未启动”“启动结果未知”。重试复用已落盘消息，不重复追加；请求结果未知先查询运行状态 | 编辑器保存冲突、存储失败、主进程启动失败、网络断连、重复回调；失败不得拿旧磁盘正文继续执行 |
| KB-11 | UI 在第一个 await 前同步占位。宿主同步预留 run/conversation，再进行异步验证和启动；项目镜像锁在同步镜像前取得，不能仅靠按钮禁用。重复请求使用稳定 request/run 身份；所有失败出口按占位所有者释放 | 启动失败重试、取消、模型切换、编辑/回退/删除历史、配额清理；旧 finally 不得释放新任务占位 |

先在现有 CodexSessionService 上明确 starting/running/terminal 生命周期，不新建另一套调度器。启动结果未知时避免再次请求模型。保留现有单项目镜像运行约束；运行中的历史删除/配额清理必须跳过或明确拒绝，不能删除任务正在使用的记录。确认快照可以供切换视图恢复，进程重启后旧批准只能显示失效/中断，不自动续批。

### 根因二：编辑器上下文既被当作提示，又被当成硬性修改范围

对应 KB-03、06。普通光标、非空选择、编辑器命令指定的范围没有一致的语义；命令文本和实际请求目标在不同时间读取。

| ID | 具体修法（待实施） | 必须检查的关联点 |
| --- | --- | --- |
| KB-03 | 区分上下文提示和明确修改范围。普通光标不产生选区锁；明确的非空 selection 才检查选区外不变；显式“在光标插入”可保留零长度 insertion 范围。前后端使用一致校验 | 普通整章修改、仅改选区、光标插入、选区失效、跨资源补丁、批准后内容变化；不得删除现有选区保护 |
| KB-06 | 编辑器命令排队时保存项目、资源、操作类型、范围和对应版本，UI 显示命令目标；发送前保存该目标并核验同一内容版本。切章节不替换目标，切项目将旧命令保留在原项目而不混发 | 保存队列必须按目标资源操作，不能只 flush 当前打开章节；延迟发送、编辑器脏稿、项目切换、重试和旧版本 |

保存后的新版本若与命令选区内容不一致，先阻断这次局部编辑并提示重新选择，不能在新内容上套用旧偏移。只冻结用户明确指定的范围，不冻结整个小说上下文；模型仍通过工具读取最新资料。用户明确请求更大范围时，需要可见地更新任务范围，而不是暗中越过原保护。

### 根因三：模型能力、项目工具挂载和写作进度被 Skill/编辑器页面间接决定

对应 KB-01、02、07。模型工具验证、当前项目上下文、挂载模式和 operation 是四个不同概念，却分别用页面状态和 Skill 名推断。

| ID | 具体修法（待实施） | 必须检查的关联点 |
| --- | --- | --- |
| KB-01 | 为项目聊天确定稳定的项目工具模式：绑定有效项目且模型工具已验证时，挂载该项目读取工具和受控补丁环境，不因打开资料页/设置页变化。无项目聊天保留文本模式；工具不可用时明确标明仅文本，不虚构操作能力 | 模型验证、订阅/API、旧 thread 指纹和一次性历史导入、项目镜像互斥、内置 Skill；模型探针和导入 one-shot 不得被全局改成可写项目任务 |
| KB-02 | 由宿主返回配置能力和本回合实际能力，UI 区分准备中、项目工具可用、仅文本及挂载失败；批准状态单独显示。未启动时不假称本回合已挂载 | 模型中心、切换模型/推理档位、连接失效、启动失败和页面切换；probe 成功不替代补丁验收 |
| KB-07 | 保存统计由运行及真实 commit 驱动，不能只有 operation=write/edit 才记录。Skill 只辅助任务，不作执行事实来源。普通后续请求在该会话中继续，新的目标/范围来自本轮明确输入，不能盲目继承旧选区 | writingProgress、taskLedger、report_writing_progress、结构化资料修改、连续保存、终态结果；不能将模型结束或有提交等同用户目标达成 |

这不是增加自然语言关键词分类器。允许项目工具不等于允许免确认写入；保持原生 apply_patch、宿主批准、范围/版本校验和新增正文限定授权。现有镜像按项目目录重建，不能为了“所有聊天有工具”同时放开同项目并行运行；如需优化读任务并行，应另做受控设计。本批先正确再评估开销。

### 根因四：宿主执行证据与聊天消息是两条没有完整衔接的数据路径

对应 KB-08、09。宿主有事件、批准和提交信息，聊天只持久化正常结束的模型文本；终态 UI 又丢弃流与工具列表。模型叙述因此替代了事实反馈。

| ID | 具体修法（待实施） | 必须检查的关联点 |
| --- | --- | --- |
| KB-08 | 用现有运行记录生成统一终态结果，计算后持久化到对应聊天回合，再通知 UI。按 itemId 更新工具记录，保留 fileChange，并区分原生工具完成与宿主正式提交。UI 展示已保存资源/拒绝/失败/未验证目标，可重开查看 | chatHistory、ledger、IPC、LAN、确认、部分提交、资料刷新；历史旧消息显示“无执行证据”，不能补造已保存结论 |
| KB-09 | 正常、失败、取消、运行时退出均走统一收尾；保留已有文本、终态、错误和 savedResources。以稳定 run/attempt/message 身份幂等保存；没有 turnId 的启动失败也可定位。为进程意外退出保留周期性检查点和提交证据 | _onNotification、_failAll、dispose、历史 ensureRuntimeMessage、重启恢复；意外崩溃只能保证最后已持久化点，不承诺未落盘的最后几个字 |

终态写入失败不能先显示“已完成”；应保留可重试收尾记录并使用已有 ledger 的 commit 证据核对，避免重试导致重复小说提交。已有 ensureRuntimeMessage 对重复消息文本有校验，不能直接复用固定 codexTurnId 来反复写检查点；需要支持同一运行的检查点更新与终态封存。保存事件是事实来源，资料面板的刷新应消费项目和资源标识，不依赖模型选择了哪个工具名字。刷新不得覆盖用户尚未处理的脏稿。

### 关联检查发现并补修

1. **原生补丁格式衔接**：批准事件可带无行号 `@@`，完成事件转换为带行号 unified diff。原校验误拒合法补丁。现在只接受能唯一精确定位的上下文块；批准与完成按资源、操作、before/after 哈希核对，正式镜像内容再核对一次。重复上下文、无定位、越界和内容改变仍拒绝。
2. **编辑器被刷新清空**：全量章节树刷新重新生成章节 ID，导致打开的 tab 失去章节。实际截图发现后修复为保留章节身份、刷新已加载正文、忽略迟到的树快照并保留脏稿。最终 UI 断言保存后编辑器仍显示最新正文。
3. **资料刷新口径**：人物卡、世界观等统一按正式提交资源类型刷新。世界观有未保存草稿时显示冲突并禁用覆盖保存；取消编辑后读回最新版本。大纲加载绑定请求的小说，不从后来切换的全局 active 项目取路径。
4. **收尾与恢复边界**：正式事务成功即保留提交证据，后续读回失败也不丢失“已保存”事实；恢复只修补缺失/未完成记录，不批量改写旧历史。generation 防止远端页面的未持久化旧版本挡住宿主恢复状态。
5. **测试自身故障**：导入原子回滚测试依赖 chmod 制造写失败，在本运行环境中没有触发失败。改为对目标世界观正式写入注入一次 EACCES，验证前面已处理资源回滚及 staging 不标 merged；没有修改导入业务逻辑。

6. **连续补丁竞态**：最终复跑发现模型已进入下一个补丁时，宿主可能还在提交上一个补丁，镜像收集会混入后续变更。原生批准入口现在等待先前通知/提交处理完；连续创作测试刻意延迟宿主检查点，验证三次逐章提交不混合。该问题来自真实最终回归失败，不能由早先通过结果掩盖。

## 用户复现后的补修：已有人物卡更新（2026-09-22）
