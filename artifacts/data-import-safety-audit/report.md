### 源码确认、尚未补足完整用户验收的缺口

- 人物/世界观分片冲突虽然保存了候选和来源，但正式可见字段仍默认取首个值；导入 UI 仅提示冲突，没有逐字段选择、解决状态和强制关联的提交决策。保留证据不等于用户已完成事实裁决。
- 分析提交、合并、角色重建和原生 mutationService 仍有多套计划/锁/恢复规则。分析重启从 chunk checkpoint 重新构建提交计划，并未统一消费已持久化 analysis-commit；角色重建候选虽写盘，UI 的审阅恢复仍依赖 React 状态。这些不能仅凭保存了 JSON 就声称恢复链闭合。
- sourceHints 在读取时仍截取 30000 字符，单次请求预算没有统一计入提示词、线索与上下文。原文分片不越限的测试不能证明整个模型请求预算完整正确。

### 手段判断与更好的改进方向

必要且应保留的方向：停止已保存操作的重复回放；角色先准备再审阅；统一世界观 schema；明确完整/部分/失败；有界调度；三方保留用户编辑；身份与路径分离；持久 session 与正式读回。这些直接对应真实的数据损失和功能断点。

本批实现不充分或应重构的部分：另建 resourcePlan 而没有统一全部写入方的锁、版本、实际写集合和恢复；变更身份文件表示而没有迁移；把字符串引文存在/名称共现当成事实支持或身份通过；保存冲突元数据后仍默认采用一个值。原先覆盖场景通过不能证明这些设计正确；上一轮“13 项已修复”的措辞过强，撤回完整修复结论。

更合理的下一版边界：

1. **唯一存储提交层**：将所有写入入口接到共同的 canonical resource、版本、锁与 WAL；只有实际写过且仍属于本事务的资源才可回滚。现有 mutationService 本身也须与 store 协调，不能只将新模块改为调用它就宣布问题解决。导入的大资源计划与模型单次工具资源上限在接口层区分，不绕过正式领域保存语义。

### 是否在为错误路线打补丁

**有一部分确实如此：把局部提升协议称为统一业务事务后，又用局部锁、检查和状态补偿去填没有收拢的入口。上一条交付判断过早，现撤回。** 反复遇错本身不是路线错误的证据；这次相同根因在不同入口反复出现，才是具体依据。

必要且应保留的部分：原子写入/日志归属、已提交决定后的向前恢复、目录 owner 与 manifest、正式登记回执、拒绝时保存原实体，都对应真实需求。不能回到无归属回滚或仅靠 Promise.race 的实现。

没有完成的核心：run、promotion、merge session、暂存状态仍各自维护结果；finalize 和 cancel 的局部锁没有约束所有能修改同一 run 的入口。revision 目前只增加，没有作为写入前提。共同文件事务只保证一次文件修改的顺序和恢复，无法证明一个旧业务命令仍有权提交。无 ID 名称仍然是可变字段，给它加 NFKC 与歧义检查也没有变成不可变身份。这些问题不能靠再加一个分支判断宣称架构闭合。

### 需要改变的设计边界（该次审计时的方案，后续实施见下节）

1. 收拢唯一运行命令入口。start/resume、分析完成、createMerge、resolve、finalizeSession、finalize、cancel、恢复均通过同一状态转换器；每次短转换在运行租约内重读当前记录，校验 expected revision、当前状态和操作代次。长分析/复制在租约外执行，结果携带代次，回来后由同一入口裁决；旧结果不能整体覆盖运行记录。不能把长任务全部塞进大锁阻止取消。
2. 明确一个持久业务状态作为权威，UI/run 摘要、暂存状态和回执从其提交结果派生。新项目提升与已有项目合并共用取消/提交规则，禁止兼容入口在门外重写旧 run 再进入 finalize。文件恢复日志继续负责文件，不再被当成业务授权依据。
3. 在审阅计划构建时绑定不可变操作身份或已持久化的实体 ID；名称只是一项可改事实。按绑定操作处理完整实体，禁止每应用一个字段后从变化中的对象重新推断身份。旧无 ID 数据迁移也应绑定同一份审阅基线。
4. 若支持多服务/跨进程活动分析，持久化所有者/代次和可验证的活动租约；若产品只允许单所有者，就在入口实际强制该限制。读取不能仅凭本地 Map 缺项宣布另一所有者死亡。

该次审计要求先以红例约束这些边界，再沿入口验证取消确认前后的正式数据、终态和回执。当时方案尚未实施，状态为 **不可交付，需收拢业务状态权威后整改**；当次没有继续修改产品、没有子代理、提交、合并或发布。后续实施及当前结论见下节。

| 提交决定 | 新项目决定保存完整 operation/manifest/目标；已有项目决定保存完整文件计划、前 hash/后字节及 run/import/session/novel/规范目录身份。取消与 decideCommit 在同一运行命令处裁决。决定前取消不写正式资源；决定后只续交原计划并返回真实结果/原回执。 |
| 物理恢复 | owner、目标保留、manifest、具名文件事务继续负责物理归属和字节。没有登记的目录必须完整匹配清单；清单外文件、第三种字节、源目标重叠及错误身份明确停止。正式发布后的重试返回原回执，保留其后的用户编辑。 |
| 迁移与锁序 | novelId 身份租约串行登记迁移、重登记、合并执行。提交验证审阅时绑定目录，不跟随登记的新路径改目标。正式项目锁释放后再写应用投影，避免与普通元数据保存倒置。旧业务接管须依据不可逆提升记录或核实过的具名文件提交证明。 |

补全来源 `_enrichmentRunId` 从持久 review.runId 恢复，不把任意候选字段透传为来源。领域拒绝保持原 Markdown 字节。保存中的合并仍可取消；迟到回调不能盖掉已确认的取消画面；提交后取消显示实际保存回执。长执行没有被塞进大运行锁来阻塞取消。

### 结论与未验证项

本次改动收拢了产生反复局部修补的根因：所有业务状态转换进入同一权威，旧工作须重新证明执行权，名称不再承担审阅身份，提交决定承载完整不可变计划。仍需要物理文件日志与执行检查点，因为多目录保存和进程恢复无法由一个内存状态代替；它们不再各自裁决业务终态。按本节具体输入和故障边界，PA-01～04、此前三个 P1 及本轮新增反例已修复并完成用户流程验证，可在本独立树审阅交付。
